{{APIRef("Web Authentication API")}}{{securecontext_header}}

دیکشنری **`PublicKeyCredentialCreationOptions`** نشان‌دهنده شیءای است که به عنوان مقدار گزینه `publicKey` به {{domxref("CredentialsContainer.create()")}} ارسال می‌شود؛ یعنی زمانی که از `create()` برای ایجاد یک اعتبار کلید عمومی با استفاده از [Web Authentication API](/en-US/docs/Web/API/Web_Authentication_API) استفاده می‌کنید.

## ویژگی‌های نمونه

- `attestation` {{optional_inline}}
  - : رشته‌ای که ترجیح طرف متکی (relying party) را برای نحوه انتقال بیانیه گواهی (attestation statement) – یعنی ارائه شواهد قابل تأیید از صحت احراز‌کننده (authenticator) و داده‌های آن – در هنگام ایجاد اعتبار مشخص می‌کند. مقدار می‌تواند یکی از موارد زیر باشد:
    - `"none"`
      - : مشخص می‌کند که طرف متکی به گواهی احراز‌کننده علاقه‌ای ندارد. این کار ممکن است برای جلوگیری از رضایت اضافی کاربر برای رفت و برگشت به سرور طرف متکی برای ارسال اطلاعات شناسایی، یا رفت و برگشت به مرجع صدور گواهی (CA) انجام شود، با هدف روان‌تر کردن فرایند احراز هویت. اگر `"none"` به عنوان مقدار `attestation` انتخاب شود و احراز‌کننده اعلام کند که از CA برای تولید بیانیه گواهی خود استفاده می‌کند، برنامه کاربردی آن را با یک بیانیه گواهی "None" جایگزین می‌کند که نشان می‌دهد هیچ بیانیه گواهی در دسترس نیست.
    - `"direct"`
      - : مشخص می‌کند که طرف متکی می‌خواهد بیانیه گواهی را همان‌طور که توسط احراز‌کننده تولید شده است دریافت کند.
    - `"enterprise"`
      - : مشخص می‌کند که طرف متکی می‌خواهد یک بیانیه گواهی دریافت کند که ممکن است شامل اطلاعات شناسایی منحصربه‌فرد باشد. این برای استقرارهای کنترل‌شده در یک سازمان در نظر گرفته شده است که در آن سازمان می‌خواهد ثبت‌نام‌ها را به احراز‌کننده‌های خاصی گره بزند.
    - `"indirect"`
      - : مشخص می‌کند که طرف متکی می‌خواهد یک بیانیه گواهی قابل تأیید دریافت کند، اما به برنامه کاربردی اجازه می‌دهد تصمیم بگیرد که چگونه آن را دریافت کند. برای مثال، برنامه کاربردی می‌تواند بیانیه گواهی احراز‌کننده را با یک بیانیه تولید شده توسط یک CA ناشناس‌ساز (Anonymization CA) جایگزین کند تا حریم خصوصی کاربر حفظ شود.

    اگر `attestation` حذف شود، مقدار پیش‌فرض آن `"none"` خواهد بود.

- `attestationFormats` {{optional_inline}}
  - : آرایه‌ای از رشته‌ها که ترجیح طرف متکی را برای قالب بیانیه گواهی استفاده‌شده توسط احراز‌کننده مشخص می‌کند. مقادیر باید از بیشترین به کمترین ترجیح مرتب شوند و به عنوان راهنما در نظر گرفته می‌شوند – احراز‌کننده ممکن است تصمیم بگیرد بیانیه گواهی را در قالبی متفاوت صادر کند. برای فهرست قالب‌های معتبر، به [شناسه‌های قالب بیانیه گواهی WebAuthn](https://www.iana.org/assignments/webauthn/webauthn.xhtml#webauthn-attestation-statement-format-ids) مراجعه کنید.

    اگر حذف شود، `attestationFormats` به طور پیش‌فرض به یک آرایه خالی تنظیم می‌شود.

- `authenticatorSelection` {{optional_inline}}
  - : شیءای که ویژگی‌های آن معیارهایی برای فیلتر کردن احراز‌کننده‌های بالقوه برای عملیات ایجاد اعتبار هستند. این شیء می‌تواند شامل ویژگی‌های زیر باشد:
    - `authenticatorAttachment` {{optional_inline}}
      - : رشته‌ای که نشان می‌دهد کدام نوع اتصال احراز‌کننده برای احراز‌کننده انتخاب‌شده مجاز است. مقادیر ممکن عبارتند از:
        - `"platform"`
          - : احراز‌کننده بخشی از دستگاهی است که WebAuthn روی آن اجرا می‌شود (به نام **احراز‌کننده پلتفرمی**)، بنابراین WebAuthn با استفاده از یک انتقال موجود برای آن پلتفرم، مانند یک API مختص پلتفرم، با آن ارتباط برقرار می‌کند. یک اعتبار کلید عمومی که به یک احراز‌کننده پلتفرمی متصل است، **اعتبار پلتفرمی** نامیده می‌شود.
        - `"cross-platform"`
          - : احراز‌کننده بخشی از دستگاهی که WebAuthn روی آن اجرا می‌شود نیست (به نام **احراز‌کننده سیار** زیرا می‌تواند بین دستگاه‌های مختلف جابه‌جا شود)، بنابراین WebAuthn با استفاده از یک پروتکل انتقال بین‌پلتفرمی مانند بلوتوث یا NFC با آن ارتباط برقرار می‌کند. یک اعتبار کلید عمومی که به یک احراز‌کننده سیار متصل است، **اعتبار سیار** نامیده می‌شود.

            اگر حذف شود، هر نوع احراز‌کننده، چه پلتفرمی و چه بین‌پلتفرمی، می‌تواند برای عملیات ایجاد اعتبار انتخاب شود.

    - `requireResidentKey` {{optional_inline}}
      - : یک مقدار بولی. اگر `true` تنظیم شود، نشان می‌دهد که طرف متکی می‌خواهد یک [اعتبار قابل کشف](/en-US/docs/Web/API/Web_Authentication_API#discoverable_and_non-discoverable_credentials) ایجاد کند.

        این گزینه فقط برای سازگاری با نسخه‌های قدیمی نگه داشته شده است: فراخوان‌دهندگان باید به جای آن از گزینه [`residentKey`](#residentkey) استفاده کنند. اگر `residentKey` داده شده باشد و پشتیبانی شود، `requireResidentKey` نادیده گرفته می‌شود. گزینه `requireResidentKey` باید فقط در صورتی `true` تنظیم شود که `residentKey` برابر `"required"` باشد.

        پیش‌فرض `false` است.

    - `residentKey` {{optional_inline}}
      - : رشته‌ای که مشخص می‌کند طرف متکی تا چه اندازه می‌خواهد یک [اعتبار قابل کشف](/en-US/docs/Web/API/Web_Authentication_API#discoverable_and_non-discoverable_credentials) ایجاد کند.
        مقادیر ممکن عبارتند از:
        - `"discouraged"`
          - : طرف متکی ایجاد یک اعتبار سمت سرور را ترجیح می‌دهد، اما یک اعتبار قابل کشف سمت کاربر را نیز می‌پذیرد.
        - `"preferred"`
          - : طرف متکی به شدت ایجاد یک اعتبار قابل کشف را ترجیح می‌دهد، اما یک اعتبار غیرقابل کشف را نیز می‌پذیرد. عامل کاربر باید در صورت لزوم کاربر را در راه‌اندازی تأیید هویت کاربر راهنمایی کند تا یک اعتبار قابل کشف ایجاد کند. این تنظیم بر تنظیم `userVerification` اولویت دارد.
        - `"required"`
          - : طرف متکی به یک اعتبار قابل کشف نیاز دارد. اگر نتوان آن را ایجاد کرد، یک `NotAllowedError` {{domxref("DOMException")}} پرتاب می‌شود. برای جزئیات بیشتر به [فهرست استثناهای `create()`](/en-US/docs/Web/API/CredentialsContainer/create#exceptions) مراجعه کنید.

        اگر حذف شود، اگر `requireResidentKey` برابر `true` باشد، `residentKey` به طور پیش‌فرض `"required"` است، در غیر این صورت مقدار پیش‌فرض `"discouraged"` است.

    - `userVerification` {{optional_inline}}
      - : رشته‌ای که نیازمندی‌های طرف متکی را برای تأیید هویت کاربر در عملیات `create()` مشخص می‌کند. مقادیر ممکن عبارتند از:
        - `"discouraged"`
          - : طرف متکی برای به حداقل رساندن اختلال در تجربه کاربر، ترجیح می‌دهد در عملیات `create()` تأیید هویت کاربر انجام نشود.
        - `"preferred"`
          - : طرف متکی تأیید هویت کاربر را در عملیات `create()` ترجیح می‌دهد، اما اگر تأیید هویت کاربر قابل انجام نباشد، عملیات شکست نمی‌خورد.
        - `"required"`
          - : طرف متکی به تأیید هویت کاربر در عملیات `create()` نیاز دارد – اگر تأیید هویت کاربر قابل انجام نباشد، یک خطا پرتاب می‌شود.

        اگر حذف شود، `userVerification` به طور پیش‌فرض `"preferred"` است.

- `challenge`
  - : یک {{jsxref("ArrayBuffer")}}، {{jsxref("TypedArray")}}، یا {{jsxref("DataView")}} که توسط سرور طرف متکی ارائه شده و به عنوان یک [چالش رمزنگاری](https://en.wikipedia.org/wiki/Challenge%E2%80%93response_authentication) استفاده می‌شود. این مقدار توسط احراز‌کننده امضا می‌شود و امضا به عنوان بخشی از {{domxref("AuthenticatorAttestationResponse.attestationObject")}} بازگردانده می‌شود.

- `excludeCredentials` {{optional_inline}}
  - : یک {{jsxref("Array")}} از اشیایی که اعتبارهای موجود را که قبلاً به این حساب کاربری (همان‌طور که توسط `user.id` شناسایی شده است) نگاشت شده‌اند، توصیف می‌کنند. این توسط طرف متکی ارائه می‌شود و توسط عامل کاربر بررسی می‌شود تا از ایجاد یک اعتبار کلید عمومی جدید روی یک احراز‌کننده که قبلاً یک اعتبار به حساب کاربری مشخص شده نگاشت شده است، جلوگیری کند. هر آیتم باید به شکل زیر باشد:
    - `id`
      - : یک {{jsxref("ArrayBuffer")}}، {{jsxref("TypedArray")}}، یا {{jsxref("DataView")}} که نشان‌دهنده شناسه اعتبار موجود است.
    - `transports` {{optional_inline}}
      - : یک {{jsxref("Array")}} از رشته‌ها که انتقال‌های مجاز را نشان می‌دهد. انتقال‌های ممکن عبارتند از: `"ble"`، `"hybrid"`، `"internal"`، `"nfc"`، و `"usb"` (برای جزئیات بیشتر به {{domxref("AuthenticatorAttestationResponse.getTransports", "getTransports()")}} مراجعه کنید).
    - `type`
      - : رشته‌ای که نوع اعتبار کلید عمومی برای ایجاد را تعریف می‌کند. در حال حاضر می‌تواند یک مقدار واحد `"public-key"` را بگیرد، اما ممکن است در آینده مقادیر بیشتری اضافه شود.

    اگر فراخوانی `create()` در تلاش برای ایجاد یک اعتبار کلید عمومی تکراری روی یک احراز‌کننده باشد، عامل کاربر کاربر را راهنمایی می‌کند تا اعتبار را با استفاده از یک احراز‌کننده دیگر ایجاد کند، یا در صورت عدم امکان، عملیات شکست می‌خورد.

    اگر `excludeCredentials` حذف شود، به طور پیش‌فرض به یک آرایه خالی تنظیم می‌شود.

- `extensions` {{optional_inline}}
  - : شیءای حاوی ویژگی‌هایی که مقادیر ورودی برای هر افزونه درخواست‌شده را نشان می‌دهند. این افزونه‌ها برای مشخص کردن پردازش اضافی توسط کلاینت یا احراز‌کننده در طول فرایند ایجاد اعتبار استفاده می‌شوند. مثال‌ها شامل مشخص کردن اینکه آیا یک اعتبار بازگشتی قابل کشف است یا خیر، یا اینکه آیا طرف متکی می‌تواند داده‌های blob بزرگ مرتبط با یک اعتبار را ذخیره کند، می‌باشد.

    افزونه‌ها اختیاری هستند و مرورگرهای مختلف ممکن است افزونه‌های متفاوتی را تشخیص دهند. پردازش افزونه‌ها همیشه برای کلاینت اختیاری است: اگر مرورگر یک افزونه مشخص را تشخیص ندهد، آن را نادیده می‌گیرد. برای اطلاعات در مورد استفاده از افزونه‌ها و اینکه کدام‌ها توسط کدام مرورگرها پشتیبانی می‌شوند، به [افزونه‌های Web Authentication](/en-US/docs/Web/API/Web_Authentication_API/WebAuthn_extensions) مراجعه کنید.

- `hints` {{optional_inline}} {{experimental_inline}}
  - : آرایه‌ای از رشته‌ها که راهنمایی‌هایی در مورد اینکه مرورگر چه رابط کاربری باید برای ایجاد یک اعتبار کلید عمومی به کاربر ارائه دهد، ارائه می‌دهد.

    رشته‌ها می‌توانند هر یک از موارد زیر باشند:
    - `"security-key"`
      - : رابط کاربری باید استفاده از یک کلید امنیتی فیزیکی جداگانه (مانند YubiKey) را برای ایجاد اعتبار توصیه کند.
    - `"client-device"`
      - : رابط کاربری باید استفاده از یک احراز‌کننده موجود در همان دستگاهی که کاربر برای دسترسی به کلاینت RP استفاده می‌کند را برای ایجاد اعتبار توصیه کند. این مشابه مقدار `authenticatorAttachment` [`platform`](#platform) است.
    - `"hybrid"`
      - : رابط کاربری باید استفاده از یک احراز‌کننده عمومی، مانند یک برنامه احراز‌کننده مبتنی بر تلفن هوشمند، را برای ایجاد اعتبار توصیه کند. این رویکرد از رویکرد بین‌دستگاهی برای مدیریت احراز هویت، با تکیه بر ترکیبی از لپ‌تاپ و تلفن هوشمند، حمایت می‌کند.

    مقدار `authenticatorAttachment` [`cross-platform`](#cross-platform) اساساً ترکیبی از گزینه‌های `hints` یعنی `security-key` و `hybrid` است – اگر یک دستگاه بلوتوث نداشته باشد و یک RP `attachment: "cross-platform"` را مشخص کند، رابط کاربری حاصل احتمالاً مشابه رابط کاربری `hints: "security-key"` خواهد بود.

    هنگامی که چندین رشته در آرایه گنجانده می‌شود، ترتیب آنها نشان‌دهنده ترتیب ترجیح، از بالا به پایین است. مرورگرهای پشتیبانی‌کننده که به راهنمایی‌ها احترام می‌گذارند باید اولین موردی را که متوجه می‌شوند استفاده کنند.

    گزینه `hints` روشی انعطاف‌پذیرتر برای مشخص کردن ترجیحات رابط کاربری برای ایجاد یک اعتبار نسبت به گزینه [`authenticatorAttachment`](#authenticatorattachment) ارائه می‌دهد، که گزینه انتخاب‌نشده را کاملاً پنهان می‌کند. `hints` همچنین امکان نشان دادن ترجیح برای کلیدهای امنیتی یا ترکیبی را فراهم می‌کند که با `authenticatorAttachment` امکان‌پذیر نیست.

    `hints` مشخص‌شده ممکن است با راهنمایی‌های ارائه‌شده در گزینه `authenticatorAttachment` در تضاد باشد. هنگامی که `hints` ارائه‌شده با این گزینه در تضاد است، `hints` اولویت دارد. `hints` ممکن است توسط مرورگر در شرایط خاص نادیده گرفته شود، برای مثال اگر نوع احراز‌کننده راهنمایی‌شده در دستگاه کاربر قابل استفاده نباشد.

    برای برخی مثال‌های کد و رابط کاربری خاص، به [معرفی hints، درخواست‌های مبدأ مرتبط و سریال‌سازی JSON برای WebAuthn در کروم](https://developer.chrome.com/blog/passkeys-updates-chrome-129#hints) مراجعه کنید.

- `pubKeyCredParams`
  - : یک {{jsxref("Array")}} از اشیایی که انواع کلید و الگوریتم‌های امضایی را که طرف متکی پشتیبانی می‌کند، به ترتیب از بیشترین به کمترین ترجیح مشخص می‌کنند. کلاینت و احراز‌کننده حداکثر تلاش خود را برای ایجاد یک اعتبار از نوع ترجیح‌شده انجام می‌دهند. این اشیا شامل ویژگی‌های زیر خواهند بود:
    - `alg`
      - : عددی که برابر با یک [شناسه الگوریتم COSE](https://www.iana.org/assignments/cose/cose.xhtml#algorithms) است و نشان‌دهنده الگوریتم رمزنگاری برای استفاده برای این نوع اعتبار است. توصیه می‌شود طرف‌های متکی که می‌خواهند از طیف گسترده‌ای از احراز‌کننده‌ها پشتیبانی کنند، حداقل مقادیر زیر را در انتخاب‌های ارائه‌شده شامل کنند:
        - `-8`: EdDSA
        - `-7`: ES256
        - `-257`: RS256
    - `type`
      - : رشته‌ای که نوع اعتبار کلید عمومی برای ایجاد را تعریف می‌کند. در حال حاضر می‌تواند یک مقدار واحد `"public-key"` را بگیرد، اما ممکن است در آینده مقادیر بیشتری اضافه شود.

    اگر هیچ‌یک از انواع اعتبار فهرست‌شده قابل ایجاد نباشد، عملیات `create()` شکست می‌خورد.

- `rp`
  - : شیءای که طرف متکی (relying party) درخواست‌کننده ایجاد اعتبار را توصیف می‌کند. می‌تواند شامل ویژگی‌های زیر باشد:
    - `id` {{optional_inline}}
      - : رشته‌ای که نشان‌دهنده شناسه طرف متکی است. یک اعتبار کلید عمومی فقط می‌تواند برای احراز هویت با همان طرف متکی (همان‌طور که توسط `publicKey.rpId` در یک فراخوانی {{domxref("CredentialsContainer.get()", "navigator.credentials.get()")}} شناسایی شده است) که با آن ثبت شده است استفاده شود – شناسه‌ها باید مطابقت داشته باشند.

        `id` نمی‌تواند شامل یک پورت یا طرح (scheme) مانند یک مبدأ استاندارد باشد، اما طرح دامنه باید `https` باشد. `id` باید برابر با دامنه مؤثر مبدأ، یا یک پسوند دامنه آن باشد. بنابراین برای مثال اگر مبدأ طرف متکی `https://login.example.com:1337` باشد، `id`های زیر معتبر هستند:
        - `login.example.com`
        - `example.com`

        اما نه:
        - `m.login.example.com`
        - `com`

        اگر حذف شود، `id` به طور پیش‌فرض به مبدأ سند تنظیم می‌شود – که در مثال بالا `login.example.com` خواهد بود.

    - `name`
      - : رشته‌ای که نشان‌دهنده نام طرف متکی است (مثلاً `"Facebook"`). این نامی است که هنگام ایجاد یا تأیید یک عملیات WebAuthn به کاربر نمایش داده می‌شود.

- `timeout` {{optional_inline}}
  - : یک راهنمای عددی، به میلی‌ثانیه، که نشان می‌دهد برنامه وب فراخوان چقدر مایل است برای تکمیل عملیات ایجاد صبر کند. این راهنما ممکن است توسط مرورگر نادیده گرفته شود.

- `user`
  - : شیءای که حساب کاربری را که اعتبار برای آن تولید می‌شود توصیف می‌کند. می‌تواند شامل ویژگی‌های زیر باشد:
    - `displayName`
      - : رشته‌ای که یک نام نمایشی کاربرپسند برای کاربر ارائه می‌دهد (مثال: `"Maria Sanchez"`)، که در هنگام ثبت‌نام اولیه توسط کاربر با طرف متکی تنظیم شده است.
    - `id`
      - : یک {{jsxref("ArrayBuffer")}}، {{jsxref("TypedArray")}}، یا {{jsxref("DataView")}} که نشان‌دهنده یک شناسه منحصربه‌فرد برای حساب کاربری است. این مقدار حداکثر طول 64 بایت دارد و برای نمایش به کاربر در نظر گرفته نشده است.
    - `name`
      - : رشته‌ای که یک شناسه کاربرپسند برای حساب کاربری ارائه می‌دهد تا به تمایز بین حساب‌های مختلف با `displayName`های مشابه کمک کند. این می‌تواند یک آدرس ایمیل (مانند `"elaina.sanchez@example.com"`)، شماره تلفن (مثلاً `"+12345678901"`)، یا نوع دیگری از شناسه حساب کاربری (مثلاً `"ElainaSanchez667"`) باشد.

## مثال‌ها

### ایجاد یک اعتبار کلید عمومی

این مثال یک `PublicKeyCredentialCreationOptions` ایجاد می‌کند و فقط ویژگی‌های مورد نیاز را مشخص کرده و برای بقیه از پیش‌فرض‌ها استفاده می‌کند.

سپس شیء را به `navigator.credentials.create()` ارسال می‌کند تا یک اعتبار کلید عمومی جدید ایجاد کند.

```js
const publicKey = {
  challenge: challengeFromServer,
  rp: { id: "acme.com", name: "ACME Corporation" },
  user: {
    id: new Uint8Array([79, 252, 83, 72, 214, 7, 89, 26]),
    name: "jamiedoe",
    displayName: "Jamie Doe",
  },
  pubKeyCredParams: [{ type: "public-key", alg: -7 }],
};

const publicKeyCredential = await navigator.credentials.create({ publicKey });
```

یک فراخوانی موفق `create()` یک promise برمی‌گرداند که با یک نمونه شیء {{domxref("PublicKeyCredential")}} حل می‌شود و نشان‌دهنده یک اعتبار کلید عمومی است که بعداً می‌تواند برای احراز هویت یک کاربر از طریق یک فراخوانی WebAuthn {{domxref("CredentialsContainer.get()", "get()")}} استفاده شود. ویژگی {{domxref("PublicKeyCredential.response")}} آن حاوی یک شیء {{domxref("AuthenticatorAttestationResponse")}} است که دسترسی به چندین قطعه اطلاعات مفید از جمله داده‌های احراز‌کننده، کلید عمومی، مکانیسم‌های انتقال و موارد دیگر را فراهم می‌کند.

```js
navigator.credentials.create({ publicKey }).then((publicKeyCredential) => {
  const response = publicKeyCredential.response;

  // Access attestationObject ArrayBuffer
  const attestationObj = response.attestationObject;

  // Access client JSON
  const clientJSON = response.clientDataJSON;

  // Return authenticator data ArrayBuffer
  const authenticatorData = response.getAuthenticatorData();

  // Return public key ArrayBuffer
  const pk = response.getPublicKey();

  // Return public key algorithm identifier
  const pkAlgo = response.getPublicKeyAlgorithm();

  // Return permissible transports array
  const transports = response.getTransports();
});
```

برخی از این داده‌ها باید برای عملیات‌های احراز هویت آینده در برابر این اعتبار در سرور ذخیره شوند – برای مثال کلید عمومی، الگوریتم استفاده‌شده و انتقال‌های مجاز.

برای اطلاعات بیشتر در مورد نحوه عملکرد جریان کلی، به [ایجاد یک جفت کلید و ثبت یک کاربر](/en-US/docs/Web/API/Web_Authentication_API#creating_a_key_pair_and_registering_a_user) مراجعه کنید.
